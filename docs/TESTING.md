# Testing Guide

This document describes how the Stellar Bounty Board test suite is organized,
how to run tests locally, and how to add new tests for features and bug fixes.

## Test Stack

| Layer         | Framework         | Location                     |
| ------------- | ----------------- | ---------------------------- |
| Backend (API) | Vitest            | `backend/test/**/*.test.ts`  |
| Frontend      | Vitest            | `frontend/src/**/*.test.tsx` |
| E2E           | Playwright        | `playwright/**/*.spec.ts`    |
| Contract      | rust-soroban test | `contracts/test/`            |

## Quick Start

Run the full backend test suite from the repo root:

```bash
cd backend
npm install
npm test            # one-shot
npm run test:watch  # watch mode (TDD)
npm run test:coverage  # with coverage report
```

Run frontend tests:

```bash
cd frontend
npm install
npm test
```

Run Playwright end-to-end tests (requires the backend + frontend running):

```bash
npx playwright test
```

### Bounty lifecycle fixtures (#1952)

`playwright/tests/bounty-lifecycle.spec.ts` drives create → reserve → submit →
release through the real UI on **testnet doubles**:

- `playwright/support/lifecycle-api-double.ts` is an in-memory API/escrow double
  that validates each transition and the release signature. No backend, Soroban
  RPC, or funded account is involved.
- `playwright/support/lifecycle-fixtures.ts` installs a connected Freighter
  double whose signatures are deterministic and stay inside the browser.

Only the frontend dev server is required:

```bash
npm --prefix frontend run dev -- --config vite.config.ts
npx playwright test playwright/tests/bounty-lifecycle.spec.ts playwright/tests/lifecycle-fixtures.spec.ts
```

The explicit `--config vite.config.ts` avoids the stale, checked-in
`frontend/vite.config.js`, which Vite otherwise prefers over the TypeScript
config.

Setup is validated before a page is opened or the wallet can sign anything.
Invalid input throws `LifecycleFixtureError` while the spec loads, with one of
these codes: `invalid_identity`, `duplicate_identity`, `invalid_network`,
`unsafe_environment`, `invalid_url`, `wallet_mismatch`.

| Variable | Default | Validation |
| -------- | ------- | ---------- |
| `E2E_MAINTAINER_ADDRESS` | `GB5IWB…JOOK` | Valid Stellar Ed25519 StrKey (G + 55 base32 chars, CRC-16 checksum) |
| `E2E_CONTRIBUTOR_ADDRESS` | `GBE6AZ…YWSF` | Same, and must differ from the maintainer |
| `VITE_STELLAR_NETWORK` | `TESTNET` | Only `TESTNET` is accepted |
| `VITE_STELLAR_NETWORK_PASSPHRASE` | `Test SDF Network ; September 2015` | The public-network passphrase is rejected |
| `BASE_URL` | `http://localhost:3000` | `http(s)` URL on a loopback or explicitly allowed host |
| `API_URL` | `http://localhost:3001` | Same; embedded credentials are rejected |
| `E2E_ALLOWED_HOSTS` | _(empty)_ | Comma-separated extra hosts, e.g. `frontend,backend` for CI service names |

The wallet double only accepts the validated maintainer key, and the API double
asserts `x-stellar-public-key`, the signed payload, and the signature header on
release. A mismatched signer therefore fails before any signature is produced.

## Test File Conventions

- Test files live next to the source they cover, mirrored under the `test/` folder.
- File names must match `*.test.ts` (backend) or `*.test.tsx` (frontend) so Vitest picks them up.
- Snapshot files generated by Vitest are stored in `test/__snapshots__/` and committed to the repo — review them carefully before accepting changes.

Example layout:

```
backend/
├── src/
│   ├── api/
│   │   └── bounties.ts
│   └── validateBody.ts
└── test/
    ├── api.bounties.get.test.ts
    ├── api.bounties.post.test.ts
    └── validateBody.test.ts
```

## Writing a New Test

1. Identify the function or route you want to cover.
2. Create a file in the corresponding `test/` directory using the `<module>.<action>.test.ts` naming convention used by the existing suite (e.g. `api.bounties.release.test.ts`).
3. Import the function or app under test and write assertions using Vitest.

```ts
import { describe, it, expect, beforeEach } from 'vitest';
import request from 'supertest';
import { app } from '../src/app';

describe('POST /api/bounties/:id/release', () => {
  beforeEach(async () => {
    // reset in-memory state, seed fixtures, etc.
  });

  it('returns 200 and marks the bounty as released', async () => {
    const res = await request(app).post('/api/bounties/abc/release').send({
      arbiterSignature: '0x...',
    });
    expect(res.status).toBe(200);
    expect(res.body.status).toBe('released');
  });
});
```

## Coverage

Coverage is configured via Vitest defaults. Run `npm run test:coverage` and open
`backend/coverage/index.html` to inspect uncovered lines. As a rule of thumb,
new bug fixes must come with a regression test that fails before the fix and
passes after.

## Performance

The backend test suite is parallelizable. If you observe flakiness, run a single
file sequentially with `vitest run path/to/file.test.ts` to isolate the failure.

Load tests live in `scripts/load-test.js` and the baseline is captured in
`docs/loadtest-baseline.md`. Run `node scripts/load-test.js` only against a
local instance to avoid hammering the staging environment.
